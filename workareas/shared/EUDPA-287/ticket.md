# EUDPA-287: Adding a new address via address book

## Description

<p><b>As a</b> Trader<br/>
<b>I want</b> to create an address<br/>
<b>So that</b> I can select it when creating an import notification</p>

<div class="panel" style="background-color: #deebff;border-width: 1px;"><div class="panelContent" style="background-color: #deebff;">
<p><b>Description</b></p>

<p>This story stands up the Import Notification Service and the Address Book API,<br/>
and adds the first thing a trader does with them - saving an address.</p>

<p><b>What the Import Notification Service is</b></p>

<p>A new frontend that is the single front door to every import journey. Live<br/>
Animals is the first journey; more will follow. Over time INS will host the<br/>
unified dashboard and the features traders share across journeys. It does not<br/>
absorb the journey frontends - <tt>trade-imports-animals-frontend</tt> stays as it<br/>
is. INS is the shared shell - sign-in, dashboard, shared features - and routes<br/>
traders to the right journey.</p>

<p><b>What the Address Book API is</b></p>

<p>A new standalone service holding the addresses an organisation uses in its<br/>
import notifications. It is the system of record for them; nothing else stores<br/>
them. It is deliberately small - it stores addresses and answers questions about<br/>
them, and knows nothing about notifications, journeys or roles.</p>

<p><b>Addresses are untyped.</b> The service has no concept of consignor, consignee,<br/>
importer or any other role. The role an address plays on a consignment is chosen<br/>
when it is selected into a notification, not when it is saved. That is what lets<br/>
one address act as place of destination, consignee and importer on the same<br/>
consignment without being stored three times.</p>

<p><b>Addresses belong to the organisation</b>, not to the user who created them. An<br/>
address saved here is immediately available to every user in the organisation,<br/>
and for selection in future import notifications.</p>

<p><b>Note - Transporter deferred</b></p>

<p>The theme page lists Transporter as an address-book-managed type, but it does not<br/>
fit the Standard Address Block: a transporter carries an approval number, which<br/>
the block has no field for, and it is found by searching the approved commercial<br/>
transporter list (<a href="https://eaflood.atlassian.net/browse/EUDPA-119" class="external-link" rel="nofollow noreferrer">EUDPA-119</a>)<br/>
rather than typed in like an address. Rather than force it, *Transporter is<br/>
deferred out of the address book for now.* Rhys is following up with Syed (BA) and Michael (UCD) to clarify the<br/>
requirements, and it will be added back in a later slice. Nothing in this ticket<br/>
handles transporters.</p>
</div></div>

<p><b>Acceptance Criteria</b></p>

<p><b>AC1 - Both services run</b></p>

<p><b>Given</b> the workspace stack is started<br/>
<b>Then</b> the Import Notification Service and the Address Book API should each come<br/>
up healthy in the stack, from their published images<br/>
<b>And</b> <tt>make docker-compose-dev</tt> should build each from local source and<br/>
hot-reload an edit without a container restart</p>

<p><b>Note:</b> <tt>make docker-compose-dev</tt> and the stack are the <b>workspace's</b><br/>
(<a href="https://github.com/DEFRA/trade-imports-animals-workspace" class="external-link" rel="nofollow noreferrer">trade-imports-animals-workspace</a>),<br/>
not either service's. This AC needs a PR against the workspace too - adding both<br/>
services to <tt>docker/stack</tt>, the dev overlay, the <tt>make setup</tt> clone list and<br/>
the repo map in <tt>CLAUDE.md</tt>.</p>

<p><b>AC2 - Sign in with the Defra ID stub</b></p>

<p><b>When</b> I sign in<br/>
<b>Then</b> I should authenticate through the Defra ID stub, the same way<br/>
<tt>trade-imports-animals-frontend</tt> does<br/>
<b>And</b> I should reach a signed-in page in the Import Notification Service<br/>
<b>And</b> the session should expose my organisation, so pages can scope to it<br/>
<b>And</b> signing out should return me to the start page</p>

<p><b>AC3 - Service navigation</b></p>

<p><b>Given</b> I have signed in<br/>
<b>Then</b> I should see the service navigation with "Dashboard" and "Address book"<br/>
links<br/>
<b>And</b> selecting "Address book" should take me to the Address book page</p>

<p><b>AC4 - View the address book</b></p>

<p><b>Given</b> I am on the Address book page<br/>
<b>When</b> the page loads<br/>
<b>Then</b> I should see every address belonging to my organisation, in a table<br/>
<b>And</b> the table should show each address's name, address and country<br/>
<b>And</b> I should see the option to add a new address</p>

<p><b>AC5 - List endpoint</b></p>

<p><b>Given</b> the Address Book API is running<br/>
<b>When</b> {{GET /organisation/</p>
{orgId}/addresses}} is called<br/>
<b>Then</b> it should return that organisation's addresses, paginated, 25 per page<br/>
<b>And</b> the page size should be a config property on the service, not a query<br/>
parameter<br/>
<b>And</b> addresses belonging to another organisation should not be returned<br/>
<br/>
<b>AC6 - Paginating addresses</b><br/>
<br/>
<b>Given</b> the Address book page has loaded<br/>
<b>Then</b> I see the first 25 addresses<br/>
<b>And</b> I can paginate through the rest when there are more than 25<br/>
<br/>
<b>AC7 - Empty address book</b><br/>
<br/>
<b>Given</b> my organisation has not saved any addresses<br/>
<b>When</b> the Address book page loads<br/>
<b>Then</b> I should see a message telling me there are no addresses yet<br/>
<b>And</b> I should see the option to add one<br/>
<br/>

<br/>
<b>Given</b> I am on the Address book page<br/>

  of the template default.</li>
	<li>*Sign-in reuses the Defra ID stub, exactly as <tt>trade-imports-animals-frontend</tt><br/>

  <tt>defraId</tt> config block in <tt>src/config/config.js</tt> and the <tt>DEFRA_ID_*</tt> env<br/>

  stand up real Defra ID for this.</li>
	<li>The organisation claim matters more here than in a single-journey frontend -<br/>
  addresses are organisation-owned, so org scope has to be available from day<br/>
  one. The claim is <tt>currentRelationshipId</tt> on the Defra ID token - the<br/>
  animals frontend maps it to <tt>organisationId</tt> in <tt>src/plugins/auth.js</tt>. Read<br/>
  it from the session, never from the query string.</li>
	<li><b>A signed-in user always has an org (D23), so do not build null-org handling.</b><br/>
  With real Defra ID a user without an organisation is stopped by an upstream<br/>
  guard and cannot create notifications or addresses at all; the stub matches<br/>
  this by not completing sign-in without one (it shows a <tt>no-organisations</tt><br/>
  screen, auto-selects when there is one, picks when there are several). So by<br/>
  the time a request reaches INS, <tt>currentRelationshipId</tt> is present. The stub<br/>
  config can pin a specific org for dev via<br/>
  <tt>crn:firstName:lastName:organisationId:sbi:organisationName</tt>.</li>
	<li>Create <tt>trade-imports-address-book</tt> - model it on<br/>
  <tt>trade-imports-reference-data</tt> (Java / Spring Boot, MongoDB, no messaging).<br/>
  Index on <tt>orgId</tt>.</li>
</ul>
