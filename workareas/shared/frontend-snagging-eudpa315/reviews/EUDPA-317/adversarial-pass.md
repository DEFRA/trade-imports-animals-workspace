## Confirmed (14)

These survived an explicit attempt to refute them.

The most substantive is the notification-side reference collision escaping the
retry loop: `createCopyAtReference` sits one line outside the
`DuplicateKeyException` handler, so a copy onto a reference already held by an
orphan Notification fails the whole operation instead of re-minting. The
verifier also caught that the naive fix is wrong — moving the call inside the
try lets the catch's idempotency lookup see the fulfilments copy inserted
earlier in the same transaction and return it as a dedupe hit with no
Notification attached, reintroducing the half-write. Note this one is likely
moot under a single collection.

Also confirmed: the "saves an edited answer" spec never asserts the edit
persisted, and both "Sorry, there is a problem with the service" `toHaveCount(0)`
checks are dead by construction — the preceding positive assertions already fail
first in the failure case.
