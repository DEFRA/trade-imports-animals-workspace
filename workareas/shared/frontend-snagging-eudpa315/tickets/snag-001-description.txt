h2. Snag as reported

Copy as new is broken

h2. Diagnosis

Real-mode {{copy}} leaves only one of the two documents that a notification is made of. The fulfilments-side copy is written, but no paired Notification document is created at the same reference, so the copy is invisible to the dashboard list and unusable in the journey.

Copy semantics are not the same on the two sides, and this changes the shape of the decision below.

* {{backend:src/main/java/uk/gov/defra/trade/imports/animals/notification/NotificationCopyMapper.java:33-85}} deliberately RESETS logistical fields on a notification-side copy — transport (portOfEntry, arrivalDate, transporter), consignment contact address, internalReference, totalNoOfAnimals, totalNoOfPackages, species and unweanedAnimals — retaining only typeOfCommodity. Each omission carries an "intentionally omitted ... reset on copy" comment.
* The fulfilments-side copy retains EVERYTHING verbatim: {{backend:src/main/java/uk/gov/defra/trade/imports/animals/notificationfulfilments/NotificationFulfilmentsService.java:103-111}} copies {{source.getFulfilments()}} wholesale.
* So does the stub that current product behaviour is defined against: {{frontend:src/server/app/services/persistence/records/stub/lifecycle/create.js:41-50}}, a {{structuredClone}} of {{source.fulfilment}}.

Consequence for the decision below: under option (a) — POST /notifications/\{sourceRef\}/copy then PUT the fulfilments — the notification projection lands with arrival date, animal counts and contact address blanked by {{NotificationCopyMapper}} while the fulfilments the user actually sees in the journey still hold the source values. The dashboard row and the journey answers disagree until the first successful save re-projects everything from fulfilments ({{frontend:src/server/app/services/persistence/records/real/lifecycle/mutate.js:36-46}}). Option (a) is therefore not a drop-in restoration of pre-retrofit ordering: it either needs the reset mapper bypassed for this path, or the product needs to rule on whether "copy as new" resets logistical fields at all.

h2. Fix

Frontend ({{trade-imports-animals-frontend}}):

* \[edit\] {{src/server/app/services/persistence/records/real/lifecycle/create.js}} — make real-mode {{copy}} leave BOTH a notification-fulfilments document and a Notification document at one shared reference. Under option (a) this becomes a two-call sequence mirroring {{create}}: POST /notifications/\{sourceRef\}/copy for the new reference plus display fields, then PUT /notification-fulfilments/\{newRef\} with the source's fulfilments read via {{getFulfilment}}. Under option (b) this file is unchanged and the backend does the dual write.
* \[edit\] {{src/server/app/services/persistence/records/real/real.requests.test.js}} — replace the copy test at lines 358-370, which currently pins the single-call broken behaviour, with one that asserts both wire writes and that the notification-side write targets the SAME reference the copy is returned under. This is the narrowest test that would have caught the snag.

Backend ({{trade-imports-animals-backend}}) — gate option (b) only:

* \[edit\] {{src/main/java/uk/gov/defra/trade/imports/animals/notificationfulfilments/NotificationFulfilmentsService.java}} — have {{copy()}} create the paired Notification at the same minted reference inside the same transaction, so one Idempotency-Key-guarded call leaves both aggregates consistent. Not touched under option (a).
* \[edit\] {{src/test/java/uk/gov/defra/trade/imports/animals/notificationfulfilments/NotificationFulfilmentsControllerIT.java}} — integration test proving a copy is retrievable from GET /notifications (the dashboard list source) and accepts POST /notifications/\{ref\}/submit. Create the file if the repo names its fulfilments IT differently — locate the existing {{*IT}} beside the controller first.

Tests ({{trade-imports-animals-tests}}):

* \[edit\] {{tests/e2e/pages/notification-dashboard.spec.ts}} — extend the copy spec at lines 87-106: after copying, return to the dashboard, search the copied reference and assert its card is visible. This is the assertion whose absence let the regression ship.
* \[edit\] {{tests/e2e/pages/notification-view-states.spec.ts}} — add coverage that a copied notification is editable end-to-end against the real stack: open the copy, change one answer, save, and assert the journey continues rather than landing on the recoverable-error page.

h2. Acceptance criteria

* Copying a draft or submitted notification from the dashboard, then returning to the dashboard and searching the copied reference, shows the copied notification as a Draft card.
* Opening a copied notification, changing an answer and saving succeeds — the user proceeds through the journey and never sees the "Sorry, there is a problem with the service" page.
* A copied notification can be submitted, and after submission its status shows as Submitted on the dashboard.
* A copied notification can be deleted, and after deletion it no longer appears on the dashboard.
* The copied notification carries the source's answers: its hub shows the same completed sections and the same answer values as the source.
* The copy is created under a new reference number that differs from the source's, and the source notification remains on the dashboard unchanged.
* Whatever retry behaviour the gate selects is stated and tested: either resubmitting the copy form after a recoverable failure yields exactly one copy (option b), or the accepted duplicate-on-retry behaviour is explicitly pinned by a test (option a).

h2. Decision needed

Which side mints the copied notification's reference number, and where does the dual write live?

* Option (a) notification-first, mirroring {{create}}: POST /notifications/\{sourceRef\}/copy to mint the new reference and copy the display fields, then PUT /notification-fulfilments/\{newRef\} with the source's fulfilments. Frontend-only, and consistent with the "frontend adapter owns the dual write" convention documented in {{real/lifecycle/transition.js:6-10}}. But it drops the Idempotency-Key dedupe, so a retry after a recoverable 500 mints a second copy and the retry-stability contract in {{notification-actions/controller.test.js:69-84}} no longer holds in real mode.
* Option (b) backend dual write: extend {{NotificationFulfilmentsService.copy}} (or add an upsert-at-reference path to POST /notifications) so one idempotent call creates BOTH documents at one reference. Preserves the Idempotency-Key retry semantics the retrofit deliberately introduced, but moves the dual write into the backend, against the convention above, and makes this a backend + frontend change.

Pick (a) or (b) before implementation; the fix files differ by repo depending on the answer. The ruling on whether "copy as new" resets logistical fields at all (see Diagnosis, {{NotificationCopyMapper}}) belongs in the same gate.
