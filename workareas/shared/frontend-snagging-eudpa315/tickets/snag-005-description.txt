h2. Snag as reported

"The autocomplete/search stuff is clunky af"

h2. Diagnosis

The snag is a known, deliberate regression introduced by the EUDPA-288 retrofit, not an accident.

*1. The enhancement was removed on purpose.*

* {{git -C repos/trade-imports-animals-frontend show --stat bc285d71}} (contained in the retrofit merge 23f2fdb4) is titled "refactor(EUDPA-288): drop accessible-autocomplete for plain selects; commodity checkboxes (p-236)".
* Its message: "origin country and port of entry keep their server-rendered govukSelects with the enhancement stripped; transit countries becomes a single 31-country govuk checkboxes group; commodity selection renders all eight commodity-species pairs as grouped checkboxes with the whole search/filter/carry/summary apparatus removed. accessible-autocomplete dependency, bundle entry, scss import and all data attributes deleted. ... Enhanced search returns as a later round."
* It cites AUTOCOMPLETE-ASSESSMENT.md (not present in any repo or workarea — searched) and "Sam's ruling".
* The prototype work it reverted is commits 7edced0d (inc-058, country-of-origin canary) and b79c1379 (inc-059, port-of-entry rollout).

*2. Current state confirmed by reading the code, not inferred.*

* {{grep -rn "data-select-autocomplete\|selectAutocomplete" src webpack.config.js}} returns nothing. {{webpack.config.js:22-30}} has only {{application}} and {{documents}} entries; {{src/client/javascripts/}} contains only {{application.js}}. {{accessible-autocomplete}} is absent from {{package.json}}.
* frontend:{{src/server/app/sets/live-animals/journeys/linear/features/transport/port-of-entry/port-of-entry.njk:18}} renders a bare {{govukSelect}} over {{services/ports}}, whose fixture {{src/server/app/services/_capture/fixtures/ports-of-entry.json}} holds 78 records — an 80-option native dropdown once placeholder + divider are counted. That is the single worst "clunky" surface and squarely against GDS guidance for long option lists.
* frontend:{{.../features/origin/template.njk:15}}, {{.../destination-country/template.njk:13}}, {{.../port-of-exit/template.njk:13}} and {{.../addresses/create-address/create-address.njk:68}} are the same pattern over the 31-country fixtures ({{countries-origin.json}}, {{countries.json}}), i.e. 33 options each.
* frontend:{{.../transport/transit-countries/transit-countries.njk:16}} is one flat 31-item checkbox group.
* frontend:{{.../commodities/search/search.njk}} is still named and keyed "search" ({{copy.en.js:4}} {{search:}}) but contains no search box at all — just grouped checkboxes ({{search.njk:19-29}}). The controller {{search.controller.js}} has no query handling. A page called "search" with nothing to search in is exactly what a snagger would flag.

*3. The one genuine free-text search left — the address-book party picker — is also clunky by design and carries a real, untested defect.*

* {{_address-picker.njk:8-12}} states the intent: "no client JS anywhere". Search is a secondary submit button ({{_address-picker.njk:86-91}}) causing a full-page POST; results are {{PAGE_SIZE = 5}} ({{src/server/app/services/address-book/index.js:26}}) over 40 records = 8 pages.
* Pagination is server-rendered {{<a href>}} links whose query string is baked at render time from the render-time {{selectedId}} and {{query}} ({{.../party-picker/view-model/index.js:33-38}} to {{view-model/pagination/results-href.js:3-13}}). Because there is no client JS to sync them, a radio the user ticks — or a query they type — on the current page is silently discarded the moment they click a page link. The hidden {{selected}} field ({{_address-picker.njk:73-75}}) is likewise render-time only.
* No test covers this. {{hub-picker.e2e.spec.js:251}} ("carries a later-page selection...") pages FIRST and ticks SECOND, so it never exercises tick-then-page. {{party-picker.controller.test.js:80-95}} asserts only that the server bakes the *incoming* {{selected}} into the hrefs.

*4. The fix is two-repo whichever way the gate is answered.*

* The -tests suite has specs written specifically to pin the stripped state — {{tests/e2e/features/port-of-entry-select.spec.ts:16}} asserts {{option}} {{toHaveCount(80)}} under the describe "Port of entry plain select", and {{tests/e2e/features/country-of-origin-select.spec.ts:13}} asserts {{toHaveCount(33)}} under "Country of origin plain select". Restoring the enhancement invalidates both.

*Why this is not actionable as reported.*

"clunky af" does not say which surface, and the only mechanism that would fix it was removed by an explicit written assessment plus a named ruling. Reinstating it without a fresh ruling is re-litigating a closed decision by guesswork, and the scope varies enormously by answer (one webpack entry and two templates, versus five templates plus transit-countries plus the commodity page plus a client-side picker). The picker's lose-your-selection-on-paginate bug is the one sub-item that is unconditionally wrong and could be built today, but it is a fragment of the snag, not the snag.

h2. Fix

*Repo: trade-imports-animals-frontend*

Unconditional (needed whichever way the gate is answered):

* {{src/server/app/sets/live-animals/journeys/linear/features/addresses/party-picker/_address-picker.njk}} — stop pagination links silently discarding a radio ticked or a query typed on the current page. Either turn the page links into submit buttons inside the existing form (name="action" value="page-N", so the live radio and q travel with them), or add the client-side sync. The header comment at lines 8-12 states the no-JS design intent and must be updated to match whatever is chosen.
* {{src/server/app/sets/live-animals/journeys/linear/features/addresses/party-picker/party-picker.controller.js}} — if pagination becomes a submit, teach {{post()}} to recognise the page action and render that page with the live payload {{q}} + {{party}}, alongside the existing search/save branches ({{request-params.js:isSearchAction}} is the seam).

Gate-dependent (only if the ruling reinstates the enhancement):

* {{webpack.config.js}} — add a {{selectAutocomplete}} entry alongside the existing {{documents}} entry (lines 22-30). Omitting this is the classic silent 404 — the bundle never ships and nothing visibly fails.
* {{package.json}} — re-add {{accessible-autocomplete}} (was 3.0.1 pre-strip).
* {{src/client/javascripts/select-autocomplete.js}} (create) — re-create the mount-over-{{select&#91;data-select-autocomplete&#93;}} entry deleted by bc285d71 (recoverable verbatim via {{git show bc285d71^:src/client/javascripts/select-autocomplete.js}}).
* {{src/client/stylesheets/application.scss}} — re-add the accessible-autocomplete styles import removed by bc285d71.
* {{src/server/app/sets/live-animals/journeys/linear/features/transport/port-of-entry/port-of-entry.njk}} — opt the 80-option port select in via {{data-select-autocomplete}} plus the {{bodyEnd}} {{getAssetPath}} include. Placeholder and divider options must carry {{value:''}} or they leak into the suggestion list (the inc-059 lesson).
* {{src/server/app/sets/live-animals/journeys/linear/features/origin/template.njk}} — same opt-in for {{countryOfOrigin}} (33 options), if the ruling includes the 31-country selects.
* {{src/server/app/sets/live-animals/journeys/linear/features/destination-country/template.njk}} — same opt-in, if the ruling includes it.
* {{src/server/app/sets/live-animals/journeys/linear/features/port-of-exit/template.njk}} — same opt-in, if the ruling includes it.

h2. Acceptance criteria

* UNCONDITIONAL — party picker: on the consignor picker, tick the radio for a record on page 1, then click the 'Page 2' pagination control. Return to page 1: that record is still shown as the selected address, and 'Save and continue' commits it without re-ticking.
* UNCONDITIONAL — party picker: type a new term into the search box WITHOUT pressing Search, then click a pagination control. The typed term is not silently thrown away — either it is applied, or the control cannot be reached without submitting it. The user never loses typed input to a click.
* UNCONDITIONAL — party picker: the existing behaviours still hold — searching resets to page 1, a search that matches nothing shows the empty state with the query preserved, and the error summary anchors to #q when nothing matched and to #party when it did.
* GATE-DEPENDENT (if the enhancement is reinstated) — port of entry: with JavaScript on, the port field is a combobox; typing 'aberdeen' filters the list case-insensitively and typing the code 'GB ABD' surfaces the same suggestion; choosing it and saving persists the CODE, and reopening the page shows the port name back in the combobox.
* GATE-DEPENDENT — no-JS path unchanged: with {{javaScriptEnabled:false}} the same page still renders a plain govukSelect, and selecting a port and saving persists the identical value. Progressive enhancement, never a hard dependency.
* GATE-DEPENDENT — the placeholder row ('Select port of entry') and any disabled divider row never appear as suggestions in the enhanced list.
* GATE-DEPENDENT — the enhanced page has no serious or critical axe violations under wcag2a/wcag2aa.
* GATE-DEPENDENT (if the enhancement is NOT reinstated) — the commodities page no longer presents itself as a search: the feature folder, route and copy key do not use the word 'search' when the page offers only checkboxes.
* The client bundle actually ships: the webpack manifest resolves the new entry to a file on disk and the enhancement selector string is present in the built bundle. A missing bundle entry 404s silently and every server-rendered assertion still passes.

h2. Decision needed

Is this snag the "later round" that commit bc285d71 explicitly deferred — i.e. do we reinstate the accessible-autocomplete progressive enhancement (accessible-autocomplete dependency + a {{selectAutocomplete}} webpack entry + {{data-select-autocomplete}} opt-in) that EUDPA-288 deliberately deleted, and if so on exactly which surfaces (port of entry 80 options; country of origin / destination country / port of exit / create-address country ~33 options each; transit countries 31 checkboxes; commodity species 8 checkbox groups), AND does the address-book party picker also get client-side enhancement or does it keep its deliberate no-JS POST-search + link-pagination pattern with only its lose-your-selection-on-paginate bug fixed?
