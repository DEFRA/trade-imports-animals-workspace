h2. Snag as reported

The autocomplete/search stuff is clunky af

h2. Diagnosis

The snag is about search UI that EXISTS and behaves badly, not about its absence. Two shipped surfaces are the likely referents, and the investigator missed both.

*A. Notification dashboard search* — {{frontend:.../features/dashboard/template.njk:40-54}} — a Search box that only matches a complete reference number, case-sensitively. Stub: {{frontend:src/server/app/services/persistence/records/stub/lifecycle/read.js:25}} ({{journey.id === referenceNumber}}). Real: {{backend:.../notification/NotificationService.java:130-140}} via {{NotificationRepository.findByReferenceNumberAndStatusIn}} ({{NotificationRepository.java:17}}), documented as exact match at {{NotificationController.java:139}}. Typing part of a reference returns "No notifications found" — pinned at {{tests:tests/e2e/features/notification-dashboard-search.spec.ts:45-60}}. Fixing this reaches into the backend.

*B. Address-book party picker* — {{frontend:.../features/addresses/party-picker/_address-picker.njk:77-91}} — free-text {{q}} plus a secondary Search submit and a radio table paginated at {{PAGE_SIZE = 5}} over ~40 records ({{frontend:src/server/app/services/address-book/index.js:26}}), i.e. 8 pages. Every search and every page turn is a full page reload with selection smuggled through hidden fields and query strings ({{party-picker.controller.js:94-97}}, {{view-model/pagination/results-href.js}}). Shared by all five parties plus contact ({{addresses/parties.js:15-63}}). Pinned at {{tests:page-objects/notification/party-picker-page.ts:21-26}} and {{tests:tests/e2e/features/addresses-picker.spec.ts}}.

*C. Long selects have no type-ahead* — the investigator's original finding. It is real and verified, but it is a separate concern that re-opens the deliberate EUDPA-288 ruling in {{bc285d71}} ("Enhanced search returns as a later round"). It is the third item on the decision list, not the whole diagnosis.

The gate question for Sam is which surface — dashboard search matching, party-picker round-tripping, or long-select type-ahead — and only the third one is a reversal of a settled decision.

h2. Acceptance criteria

* On the arrival-details page a user can reach 'Aberdeen Harbour' by typing part of its NAME ('aberdeen') without scrolling an 80-item list, and can equally reach it by typing its CODE ('GB ABD').
* The value submitted and persisted for port of entry is still the code 'GB ABD' — reopening the page after a save shows Aberdeen Harbour selected, exactly as {{tests/e2e/features/port-of-entry-select.spec.ts}} asserts today.
* With JavaScript disabled, every enhanced control still renders as a working server-rendered govuk control and still submits and persists its value — the journey completes end to end with no client JS.
* The placeholder row ('Select port of entry' / 'Select a country') and any disabled divider row never appear as selectable suggestions in the filtered list.
* On the commodity selection page a user can narrow the visible species without leaving the page or losing species already ticked; ticking a species, narrowing again, then clearing the filter shows the earlier tick still set.
* Commodity selection still writes to the store only on 'Save and continue' — narrowing or clearing the filter never creates, removes or reorders a commodity line.
* Submitting the commodity page with nothing selected still renders the 'Select a commodity' error summary, and clicking that link focuses the first species control.
* Every changed page has no serious or critical axe violations under wcag2a plus wcag2aa, in both the empty and the error state.
* Each enhanced control still exposes an accessible name matching its visible label ('Port of entry', 'Country of origin') to assistive technology.
* No spec anywhere asserts the ABSENCE of a search affordance — the two assertions at {{commodities/e2e/search.e2e.spec.js:54}} and {{:57}} are gone, and the two tests-repo specs are no longer named 'plain select'.

h2. Decision needed

Which long-list controls get a search affordance, and which mechanism?

Pick a *scope*:

* (a) port of entry only (80 options, the worst offender)
* (b) all six ports/countries selects
* (c) the commodity selection page only
* (d) all of the above

AND a *mechanism*:

* (1) restore the pre-288 {{accessible-autocomplete@3.0.1}} progressive enhancement exactly as built in {{7edced0d}}/{{b79c1379}} — proven here, works with JS off, but is a third-party control outside the govuk toolbox and was ruled out once already. If this is the pick, what changed?
* (2) a different client-side component, e.g. MOJ Frontend's {{multi-select}}/{{filter}}, already a dependency
* (3) a server-rendered search page with no client JS — what the commodity page was pre-288: a Search button and a full round-trip per keystroke-batch
* (4) restructure instead of enhance — e.g. split ports by region, or add a commodity-category step before the species checkboxes, so no list is ever long enough to need searching

Also needed: does {{AUTOCOMPLETE-ASSESSMENT.md}} still stand, and if it ruled the enhancement out on accessibility grounds, does that ruling now apply to whatever replaces it?
