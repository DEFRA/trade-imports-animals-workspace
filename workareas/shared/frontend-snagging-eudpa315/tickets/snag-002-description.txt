h2. Snag as reported

Copy as new CSS is off

h2. Diagnosis

The reported symptom is a layout defect, not a font defect. On the notification dashboard the summary-card action row wraps, so "Copy as new" drops onto its own line and reads as broken.

The dashboard is rendered inside a hard-coded two-thirds grid column. {{src/server/app/shared/layout.njk:57}} sets {{govuk-grid-column-two-thirds}} for every page with no per-page override, so after the layout retrofit the dashboard lost the full-width container it previously had. The filter panel is a fixed 280px, which leaves the results list too narrow at desktop to fit View, Amend, Copy as new and Delete with their separators on one line.

An earlier investigation attributed the snag to a font-family regression: {{src/client/stylesheets/core/_main.scss:16}} declares {{font-family: inherit}} on {{.app-link-button}}, emitted after {{.govuk-link,a\{font-family:GDS Transport,arial,sans-serif\}}} at equal specificity (compiled bundle bytes 137469 vs 941), so it wins, and no ancestor supplies a family (govuk-frontend 6.4.0 sets font-family per component class only — {{.govuk-summary-card__actions}} sets font-size and font-weight but not family). Verified live at 1440px: {{.app-link-button}} computes {{Times}} while its sibling {{a.govuk-link}} actions in the same {{<ul>}} compute {{"GDS Transport", arial, sans-serif}}.

That font-family finding is real, but it is a separate defect and is not what "Copy as new CSS is off" describes. This subtask covers the layout width only. {{.app-link-button}} and {{.app-form-inline}} are not changed here.

h2. Fix

h3. trade-imports-animals-frontend

* {{src/server/app/shared/layout.njk}} — replace the hard-coded {{govuk-grid-column-two-thirds}} at line 57 with a per-page content width, e.g. {{\{% set contentColumnClasses = contentColumnClasses | default("govuk-grid-column-two-thirds") %\}}} and render {{<div class="\{\{ contentColumnClasses \}\}">}}. Child templates set the variable at top level, the same idiom the pre-retrofit layout used for {{mainClasses}}. The default stays two-thirds so every form page is unchanged.
* {{src/server/app/sets/live-animals/journeys/linear/features/dashboard/template.njk}} — add {{\{% set contentColumnClasses = "govuk-grid-column-full" %\}}} at the top of the template so the dashboard renders full width again, as it did before the retrofit. No other change to the template — the action markup and {{.app-link-button}} are correct as they stand.
* {{src/server/app/shared/layout.test.js}} — extend the existing nunjucks render test: assert the layout renders {{govuk-grid-column-two-thirds}} by default, and renders {{govuk-grid-column-full}} when a page sets {{contentColumnClasses}}. This is the narrowest regression guard for the root cause.
* {{src/server/app/sets/live-animals/journeys/linear/features/dashboard/dashboard.e2e.spec.js}} — add a desktop-viewport test that the summary-card action row does not wrap: locate the four actions for a submitted notification (the file already has the {{actionFor}} helper at lines 111 and 127) and assert every action's {{boundingBox().y}} is equal, i.e. all four including "Copy as new" sit on one line. Self-contained, raw locators, auto-waiting — no sleeps, no page objects.

h2. Acceptance criteria

* The notification dashboard renders across the full width of the page container at desktop, not inside a two-thirds column
* On a desktop viewport, all of a submitted notification's card actions — View, Amend, Copy as new, Delete — render on a single line with their separators, with "Copy as new" neither wrapped onto its own line nor clipped
* The dashboard filter panel and the results list sit side by side at desktop, with the results list wider than the 280px filter panel
* Single-question journey pages still render in a two-thirds column — the layout default is unchanged and no existing page moves width unless it opts in
* Copy as new still posts and still looks identical to the neighbouring View and Delete links (same colour, weight, underline and focus state) — no change to {{.app-link-button}} or {{.app-form-inline}}
* No new client-side JavaScript is introduced; the page behaves the same with JavaScript disabled
