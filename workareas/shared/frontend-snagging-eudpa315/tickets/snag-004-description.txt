h2. Snag as reported

MoJ date picker is used but doesn't have restricted dates

h2. Diagnosis

Confirmed real, and it is not an EUDPA-288 regression — the restriction has never existed ({{git -C repos/trade-imports-animals-frontend log --all -S minDate}} returns nothing; a grep for {{minDate}} / {{maxDate}} / {{excludedDates}} / {{excludedDays}} / {{weekStartDay}} over {{src/}} and {{prototypes/}} returns nothing).

There are exactly three MoJ date pickers in the live-animals journey, all rendered through one shared helper:

* {{frontend:src/server/app/sets/live-animals/journeys/linear/features/exit-date/template.njk:13}} → {{mojDatePicker(exitDate)}}, params built at {{.../exit-date/controller.js:34-39}}
* {{frontend:src/server/app/sets/live-animals/journeys/linear/features/transport/port-of-entry/port-of-entry.njk:16}} → {{mojDatePicker(arrivalDate)}}, params built at {{.../port-of-entry/port-of-entry.controller.js:86-91}}
* {{frontend:src/server/app/sets/live-animals/journeys/linear/features/documents/template.njk:41}} → {{mojDatePicker(dateOfIssue)}}, params built at {{.../documents/view-model/render.js:58-63}}

h3. Root cause, layer 1 (client)

Every one of those calls {{kit.dateField}} at {{frontend:src/server/app/shared/kit.js:158-168}}, which returns only \{ id, name, classes, label, hint, errorMessage, value \}. The MoJ 10.0.1 component reads its restrictions from {{params.minDate}}, {{params.maxDate}}, {{params.excludedDates}}, {{params.excludedDays}} and emits them as {{data-min-date}} / {{data-max-date}} / {{data-excluded-dates}} / {{data-excluded-days}} ({{node_modules/@ministryofjustice/frontend/moj/components/date-picker/template.njk:10-36}}). {{dateField}} has no parameter for any of them and no caller passes one, so every calendar renders fully open — any past or far-future date is selectable.

h3. Root cause, layer 2 (server)

The only date rule enforced on POST is calendar validity. {{dateText}} ({{frontend:src/server/app/lib/validate/validators.js:190-203}}) matches {{^(\d\{1,2\})/(\d\{1,2\})/(\d\{4\})$}} and calls {{isRealDate}} ({{frontend:src/server/app/lib/validate/calendar.js:8-24}}); there is no bounded-date validator in {{validators.js}} at all (the exported set is compose/requiredText/requiredExactDigits/optionalText/maxText/pattern/postcode/vehicleReg/ukPhone/requiredOneOf/oneOf/integerInRange/dateParts/dateText). All three controllers use it unbounded: {{exit-date/controller.js:21}}, {{port-of-entry.controller.js:51}}, {{documents/form/payload.js:23}}. So even once {{data-min-date}} lands, a JS-off user or a direct POST still saves an out-of-range date — the fix has to be both layers or it is cosmetic.

h3. Why this is needs-decision and not actionable

Nothing in the repo or the requirement source states what "restricted" means for these fields. The mined Confluence source of truth ({{workareas/journey-builder/EUDPA-249/extract.confluence-v4.json:426-436}} for {{arrivalDateAtPort}}, {{:662-675}} for {{accompanyingDocumentDateOfIssue}}) records {{conditionsRaw: "Must be a valid date in DD/MM/YYYY format"}} and nothing more; {{exitDate}} does not appear in the extract at all. The obligations carry no constraint either ({{frontend:src/server/app/sets/live-animals/obligations/sections/arrival.js:5-9}} is \{id, name, status: 'mandatory'\}). The three fields plainly want different rules — an expected exit date and an expected arrival at port are forward-looking, a document date of issue is backward-looking — and picking those bounds is a policy call, not a mechanical one. Guessing would also silently change validation of already-saved notifications.

h3. Blast radius that makes this a two-repo fix

Absolute dates are hard-coded either side of any future-only rule, and today is 2026-08-07 so some are already in the past. {{frontend:src/server/app/sets/live-animals/journeys/linear/features/transport/e2e/arrival-transit.e2e.spec.js:68}} fills {{03/01/2026}}; {{tests:flows/journey.ts:143}} fills {{12/12/2026}}; {{tests:tests/e2e/journeys/persistence/persistence-accompanying-document.spec.ts:29}} pins \{day:'3', month:'1', year:'2026'\}. Any min-date rule turns those into fixtures that rot with the calendar, so they must move to dates computed relative to now as part of the same change.

h2. Acceptance criteria

* On the exit date page, the date picker calendar does not offer any date outside the agreed exit-date range — out-of-range days are not selectable and cannot be reached by paging the calendar.
* On the arrival details page, the arrival date picker calendar does not offer any date outside the agreed arrival-date range.
* On the upload documents page, the date of issue picker calendar does not offer any date outside the agreed date-of-issue range.
* Typing an out-of-range date directly into any of the three inputs and submitting the form re-renders the page with a GOV.UK error summary at the top, the agreed error message, a summary link that moves focus to that input, and the typed value preserved in the field.
* The out-of-range rejection happens with JavaScript disabled and on a direct POST — the restriction is not achievable by bypassing the client-side picker.
* An in-range date still saves and the journey advances exactly as it does today; no existing valid answer is newly rejected.
* A date that is inside the allowed range but not a real calendar date (for example 31/2/2026) still produces the existing 'Enter a real …' message, not the new out-of-range message.
* Every new error message exists in both English and Welsh copy files with identical structure.
* Leaving any of the three date fields blank behaves exactly as it does today — the bound does not make an optional field mandatory or a mandatory field pass early.

h2. Decision needed

The requirement source (Confluence "Live Animals Data Fields V4") says only "Must be a valid date in DD/MM/YYYY format" for the two documented fields, and does not mention {{exitDate}} at all, so no bound can be derived from it. For each of the three pickers we need a ruling on (a) earliest allowed date, (b) latest allowed date — both expressed relative to today, e.g. "today", "today + 1 day", "today + 12 months", "no upper bound" — (c) whether any days or specific dates are excluded (weekends, bank holidays — MoJ supports {{excludedDays}} / {{excludedDates}}), and (d) the exact GDS error message for each out-of-range case, in English and Welsh.
