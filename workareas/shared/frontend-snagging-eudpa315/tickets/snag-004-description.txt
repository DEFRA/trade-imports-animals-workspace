h2. Snag as reported

MoJ date picker is used but doesn't have restricted dates

h2. Diagnosis

All three MoJ date-picker fields in the live-animals journey are unrestricted, in both the widget and the server-side validation.

* {{kit.dateField}} (frontend:src/server/app/shared/kit.js:158) passes no {{minDate}} / {{maxDate}} to the MoJ macro. The macro reads those at {{template.njk:10-33}}, so with nothing supplied the calendar offers every date.
* {{dateText}} (frontend:src/server/app/lib/validate/validators.js:190) applies no upper or lower bound — it only checks the value is a real calendar date. A typed out-of-range value is therefore accepted and saved.
* The three affected fields are {{arrivalDateAtPort}} (transport / port-of-entry), {{exitDate}} (exit date) and {{accompanyingDocumentDateOfIssue}} (add a document).

Because both legs are unbounded, a fix needs a view leg (bounds reaching the MoJ macro) and a server leg (bounds enforced on the typed value).

h3. What the rule is likely to look like

The analogous IPAFFS arrival-date rule is a window that PERMITS PAST DATES, not a future-only rule:

* CHED-D — "5 days in the past or 120 days in the future" (workareas/trace-requirements/ched-d/journey-spec.json:7939), evidenced against legacy {{arrival_date_validator.js:43-49}} with a per-CHED-type {{futureDateLimit}} at {{:18-22}}.
* CHED-P — "30 days in the past or 180 days in the future" (workareas/trace-requirements/ched-p/journey-spec.json:16573).

Live animals is CHED-A and has no trace file in the workspace, so the CHED-A numbers are genuinely unknown. The open question is therefore "what is the CHED-A arrival / exit / issue window, and can we recover it from the legacy validator's per-type table?" — not a choice between two future-only rules. Any ruling that forbids backdating outright would diverge from the legacy behaviour for the other CHED types.

h3. Two further points the ruling must settle

* Backend enforcement — backend:src/main/java/.../accompanyingdocument/DocumentUploadRequest.java:27 persists {{dateOfIssue}} as an unconstrained {{LocalDate}}. The ruling must say whether the bound is also enforced at the API, or frontend-only.
* Hint copy — the EN and CY hint examples on the arrival and exit pages ("For example, 27/3/2026") are already past dates and become self-contradictory under any forward-leaning rule.

h2. Acceptance criteria

* The date-picker input on the exit date, arrival details and add-a-document pages each render with the restriction attributes the ruled range implies ({{data-min-date}} and/or {{data-max-date}}), so the calendar offers only dates inside that range and dates outside it cannot be clicked.
* Typing a date outside the ruled range into any of the three pickers and submitting the form re-renders the page with a GDS error summary and an inline error against that field, and the answer is not saved.
* Typing a date inside the ruled range still saves and advances exactly as it does today, including the existing 'Enter a real <field> date' behaviour for calendar-invalid input such as 31/2/2026.
* Leaving an optional date blank is still accepted — the range rule does not turn an optional field into a required one.
* The out-of-range error message exists in both English and Welsh copy with identical structure, and the copy-parity convention test passes.
* No spec in either repo depends on a hardcoded absolute date that will fall outside the ruled range as the wall clock advances.

h2. Decision needed

The valid range for each of the three date fields, and whether the rule binds the calendar widget only or the typed value too.

h3. (a) arrivalDateAtPort

* What is the earliest allowed arrival date — today, tomorrow, or a backdated window as legacy allows for other CHED types (CHED-D 5 days in the past, CHED-P 30 days)?
* Is there a maximum lead time (for example today + 12 months, or a CHED-A-specific {{futureDateLimit}} equivalent to CHED-D's 120 days / CHED-P's 180 days)?
* Can the CHED-A numbers be recovered from the legacy validator's per-type {{futureDateLimit}} table rather than invented?

h3. (b) exitDate

* What is the earliest allowed exit date?
* Must it be strictly after {{arrivalDateAtPort}}, or is same-day exit allowed?
* Does the temporary-admission-of-horses stay limit impose a maximum (for example arrival + 90 days)?

h3. (c) accompanyingDocumentDateOfIssue

* Is today allowed as a date of issue?
* Is any future date rejected?
* Is there an earliest allowed issue date (for example a maximum document age)?

h3. Enforcement and wording

* Confirm that out-of-range typed values must be rejected server-side with an inline error, not merely greyed out in the calendar.
* Confirm whether the bound is also enforced at the backend API ({{DocumentUploadRequest.dateOfIssue}} is currently an unconstrained {{LocalDate}}).
* Supply the GDS error wording for each rejection — one message per field per bound breached, in English and Welsh.
* Confirm the replacement hint examples for the arrival and exit pages, since the current "For example, 27/3/2026" examples are past dates.
